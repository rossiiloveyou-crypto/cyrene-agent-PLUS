## 二、修正一 ★ 关于桌面对话绑定 —— 真实情况和我上一轮说的**是反的**

### 我上一轮的错误表述

我说：*"作者保留 `conversation-binding-api.ts`，把它当作 journal 的写入目标 → 建议保留官方语义，成本几乎为零。"*

这个表述**误导了你**，让你以为"保留"意味着要把删掉的东西加回来。**实际不是。**

### 核查后的真实情况

我用 grep 逐层追完了整条绑定链路，事实如下：

| 环节 | 官方树的实际情况 | 判断 |
|---|---|---|
| `conversation-binding-api.ts`（3 个导出） | 引用者**只有 2 个**：它自己的测试 + `init.ts:24-27` | 薄封装，无其他消费者 |
| `init.ts:323-341` | 3 个 IPC handler（GET / BIND / UNBIND） | 只是把 API 转成 IPC |
| `preload/index.ts:403-406` | 3 个 preload 暴露方法 | 只是转发 |
| **renderer 侧调用者** | **0 个**（全 `src/renderer` 检索 `CHANNELS_CONTEXT_*` 无匹配） | **官方作者自己把绑定 UI 删了** |
| `bootstrap.ts:98-101` | `resolveBoundConversationId` 存在，读 `store.resolve(sessionId)` | 但**没有任何代码调用 `store.bind()`** → 永远返回 `null` |
| `channel-context.ts:21-22` | `resolveChannelConversationTarget` | 绑定为 null 时回退 `sessionId` ✔ |
| `conversation-binding-store.ts` | `bind()` 方法仍在，但唯一调用者是即将被删的 API | bind 路径实际已死 |

**结论：官方作者删了绑定 UI，却忘了删身后的 IPC 管道。你删掉 `conversation-binding-api.ts` + 3 个 `CHANNELS_CONTEXT_*` 常量，做的正是作者没做完的收尾。**

所以 —— **你问"再加回来不会麻烦吗"，答案是：根本不需要加回来。你的删除是对的，应该保持。**

### 重要：但 store 不能删！它被你的「区块」功能依赖

这是核查中发现的**关键依赖**，如果不查清楚会导致误删你的保护功能：

```
src/main/zones/zones-ipc.ts
  Line 10:  import { getChannelConversationBindingStore } from "../channels/conversation-binding-store";
  Line 112: const bindingSnapshot = getChannelConversationBindingStore().list();
  Line 115:   externalChats: bindingSnapshot.externalChats,
```

**你的 zones（区块）用 store 的 `externalChats` 作为「记忆区块成员选择器」的数据源** ——
正是你要求"不要动"的功能之一。

所以要把两件事分开看，它们在同一个文件里但互不相干：

| store 里的东西 | 谁在用 | 处置 |
|---|---|---|
| `externalChats` + `observe()` + `list()` + `flush()` | **你的 zones** | ✅ **必须保留** |
| `bindings[]` + `bind()` + `unbind()` + `resolve()` | 只有待删的 API | 可留可删，无害 |

### 两个方案的同等结论

| 方案 | 要对 `conversation-binding-store.ts` 做什么 | 要对 `bootstrap.ts` 做什么 | 额外工作量 |
|---|---|---|---|
| **甲：官方 store 原样保留** | 零改动 | 保留官方 `resolveBoundConversationId`（永远返回 null） | **≈0** |
| **乙：用你的 163 行精简版** | 需改写官方 212 行 | 同上 | 小 |

**推荐选甲** —— 零冲突、零心智负担。绑定管道保持"存在但永不可达"的状态即可，
`resolveChannelConversationTarget` 会自动回退到 `sessionId`，行为与你的意图完全一致。

### 修正后本议题的最小改动面（比预想小得多）

| 动作 | 文件 |
|---|---|
| 接受你的删除 | `conversation-binding-api.ts`、`conversation-binding-api.test.ts` |
| 从官方 `init.ts` 移除 | 3 行 import（`:24-27`）+ 3 个 handler（`:323-341`） |
| 从官方 `ipc-channels.ts` 移除 | 3 个常量（`:438-440`） |
| 从官方 `preload/index.ts` 移除 | 3 个暴露方法（`:403-406`） |
| **完全不需要碰** | `channel-context.ts`、`dispatcher.ts`、`conversation-binding-store.ts`、`bootstrap.ts` |

> 顺带一个发现：官方 `conversation-binding-api.ts` 里的中文错误文案是**乱码**
> （如 `"璇锋眰鏍煎紡鏃犳晥"` 实为"请求格式无效"）。既然要删，无需关心。

## 三、修正二 ★ 关于"群聊旁听"的迁移可行性 —— 已启动专项核查

你已同意迁移到 CTA，所以现在**必须回答**决定性问题：

> 作者的 CTA 轨迹系统（`ConversationTranscriptStore` / `Projection` / 校验器）能否安全地
> 新增一种"**未触发的群消息（旁听）**"条目类型，而不破坏投影、校验、压缩与快照？

这**不是**可以拍脑袋决定的事，因为已知：
- `TranscriptEntry` 是**判别式联合类型**，每种 kind 有严格校验（`assertValid*` / `hasOnlyKeys` / `optionalField`）
- 官方全库检索 `旁听|observedOnly|observedMessage|triggered` = **0 命中**，确认无现成机制
- 若某个校验器是 **fail-closed**（遇到未知 kind 直接拒绝），硬加新类型会导致轨迹读取失败

**已委托专项分析**，要求给出三个备选方案的明确对比与推荐：

| 方案 | 思路 | 预计改动面 |
|---|---|---|
| **1** | 新增 `observed_message` 条目类型 | 取决于投影是否遍历全部条目 |
| **2** | 在现有条目上加一个可选字段承载旁听信息 | 可能更小 |
| **3** | **旁挂（sidecar）**：不动轨迹结构，在 `journal.buildModelContext()` 返回后把旁听摘要合并进 `modelContext` | 可能最小、零 schema 风险 |

**待确认的核心技术点**：`conversation-transcript-projection.ts`（831 行）是
**遍历全部条目**构建上下文，还是**只挑特定 kind**？如果是后者，新增 kind 天然被忽略 → 方案 1 就非常安全。

**Phase 6 开始前必须先拿到这个结论** —— 否则可能白写一遍再推翻。
