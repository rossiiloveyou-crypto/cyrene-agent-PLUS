## §1 三条第一原则

### 原则 1 · 为 agent 的可读性而写，不为人的美观而写

蓝图是**给 agent 读的执行手册**。判据：

- 每条改动能落到 `文件:行号`，或落到一条**可粘贴执行**的命令
- 禁止「优化一下相关逻辑」「按需处理」这类无法执行的表述
- 表格优先于散文；命令优先于描述；数字优先于形容词

### 原则 2 · 每步必须可判定，且失败必须能停

**任何一步都要附一条可执行命令**，并且：

| 要求 | 说明 |
|---|---|
| 输出可判定 | 数字比对 / 退出码 / 字符串存在性 |
| 有期望值 | 写清「期望 = 多少」，不是「应该没问题」 |
| 有容差 | 会随时间涨的量（审计行数、语料字节）必须写明容差或改成相对判据 |
| 有停止条件 | 不满足时**立即停止并报告**，不得带着失败进入下一 Phase |
| 有失败处置 | 不是 26 时该查什么、该回退到什么状态 |

### 原则 3 · 承认蓝图可能错，并把纠错机制写进蓝图

你无法预知蓝图是否绝对正确。因此在**总蓝图与每个 Phase**里都必须写明：

> 执行者应根据实际情况判断方案正误；发现错误时**明确指出、写入完成报告**；
> 遇到真实代码与蓝图冲突时，**以真实代码为准**。

这条不是客套——实战中它抓出的最大一类缺陷（例：控制台删除漏删向量、她的复述行不在擦除范围）
都是**蓝图本身没预见到**的，靠执行者的现场判断才发现。

## §2 全局约束（所有 Phase 共同遵守）

### 2.1 工具与工作区边界

| 规则 | 说明 |
|---|---|
| **只读优先** | 分析类工作（审计、比对、核查）不得写文件 |
| **不碰工作区内容** | 除明确要求改动的文件外，不得 `checkout` / `reset --hard` / `stash push` |
| **非 ASCII 文件名** | 文件名含中文时**禁止逐文件脚本复制**（会静默丢文件）；用 `git` 机制或 `robocopy` |
| **文件遍历** | 一律用 `git ls-files` / `git ls-tree` / `findstr`，不要 `Get-ChildItem` 递归拼路径 |
| **不可逆动作先备份** | 任何"销毁"类动作之前，先做**外部**备份并记下路径（应用内备份可能正是被销毁的对象） |

### 2.2 命令执行规范

```powershell
# 每条命令前显式设置编码（避免中文乱码）
[Console]::OutputEncoding = [System.Text.Encoding]::UTF8
$OutputEncoding = [System.Text.Encoding]::UTF8

# 本机是 PowerShell 5.1（无 pwsh）：不能用 &&，括号表达式里不能用 ; 连接命令
# 文件遍历一律用 git（不要 Get-ChildItem 递归拼路径）
git -c core.quotepath=false ls-files --others --exclude-standard

# 判定 robocopy 成功：看汇总的 FAILED 与 Mismatch 列，不看退出码（9 可能是假警报）
```

### 2.3 环境陷阱（详见经验库-具体坑）

编码、`2>&1` 污染变量、非 ASCII 路径转义、`NUL` 幻影目录、Node 版本不随会话传播——
都属**已实测复现过**的坑。写进蓝图时必须**直接给出规避写法**，不要只写"注意"。
（按技术栈查 [BLUEPRINT-经验库-具体坑.md](BLUEPRINT-经验库-具体坑.md)；跨语言的形状见 [BLUEPRINT-经验库-通用.md](BLUEPRINT-经验库-通用.md) §6。）

### 2.4 提交粒度

- 每个 Phase 结束后**单独提交一次**（便于回退到任意 Phase 边界）
- 提交信息格式：`<域>(P<n>): <做了什么>`
- **禁止**把多个 Phase 混在一个提交里
- **若任务本身要求"不提交"**（例如合并冲突未解决完），必须在每个 Phase 明确写出"仍不要提交"

## §3 文档族与命名规范

### 3.1 三类文档的分工（缺一不可）

| 文档 | 读者 | 职责 | 什么时候写 |
|---|---|---|---|
| **总蓝图** | 执行者 | 索引 + 全局约束 + 已拍板决策 + 当前基线 | 开工前，之后**持续同步** |
| **施工蓝图** | 执行者 | 本 Phase 怎么改、怎么验、怎么退 | 执行前 |
| **完成报告** | 下一个 Phase 的执行者 | 实际发生了什么、与蓝图差在哪、交接什么 | 执行后**立即** |

### 3.2 命名规范（实测口径）

| 类型 | 命名 | 放哪 | 示例 |
|---|---|---|---|
| 总蓝图 | `BLUEPRINT-总蓝图.md` | `task-<任务名>/` | 同左 |
| 施工蓝图 | `PHASE-<n>-<主题>.md` | `task-<任务名>/` | `PHASE-4-处理删除类冲突.md` |
| 完成报告 | `PHASE-<n>-完成报告.md` | `task-<任务名>/` | `PHASE-4-完成报告.md` |
| 决策/审计文档 | `NN-<主题>.md` | `task-<任务名>/` | `01-已拍板决策与技术修正.md` |
| 人工验证台账 | `HUMAN-人工验证台账.md` | `task-<任务名>/` | 跨 Phase 累积，H-nn |
| 写作规范 | `BLUEPRINT-撰写规范.md` | `methodology/` | 本文件 |
| 经验库（通用） | `BLUEPRINT-经验库-通用.md` | `methodology/` | H + M，写蓝图前必读 |
| 经验库（具体坑） | `BLUEPRINT-经验库-具体坑.md` | `methodology/` | L，按技术栈分章 |
| 经验库（全量台账） | `BLUEPRINT-经验库-全量台账.md` | `methodology/` | 全量 + 出处，只用于溯源 |
| 回写规范 | `BLUEPRINT-回写规范与清单模板.md` | `methodology/` | T1–T4 + 四列清单模板 |
| 文档模板 | `模板-<文档类型>.md` | `methodology/` | `模板-完成报告.md` |
| 跨阶段总览 | `<域>-overview.md` | 见 `docs/construction/` | — |

> **不要用**「PHASE-3-执行合并.md」这类**主题名不表明文档类型**的写法——
> 它让「这是蓝图还是报告」只能靠打开文件才知道。（历史遗留，不再新增。）

### 3.3 目录分离：方法论 与 任务 必须分目录（**v2.2 新增，硬要求**）

**两个目录，职责互斥**：

| 目录 | 放什么 | 跨任务复用 |
|---|---|---|
| **`methodology/`** | 规范、经验库、回写规范、文档模板、读取指令 | ✅ **整体拷到另一个任务，无需改动即可用** |
| **`task-<任务名>/`** | 总蓝图、阶段蓝图、完成报告、决策/审计文档、该任务的人工台账 | ❌ 只属于这一次任务 |

**为什么必须分**：混在一起时，新任务的 agent 会读到**上一个任务的基线数值与已拍板决策**，
把别人的结论当自己的约束——这是"经验越用越错"的主要来源。

**读取指令 = 按角色给最小必读集**（不搞"全都读一遍"）：

| 角色 | 最小必读集 | 份数 |
|---|---|---|
| **执行阶段的人** ★基准 | ① 规范**相关章节**（§4 / §5 / §8 / §10 的 T1–T4）② `task-<任务名>/BLUEPRINT-总蓝图.md` **相关节** ③ **本阶段蓝图** | **3 份**（阶段蓝图的「前置条件」已内嵌"上阶段回写清单无未勾选项"的检查命令） |
| **写蓝图的人** | ① `methodology/BLUEPRINT-撰写规范.md` ② `methodology/BLUEPRINT-经验库-通用.md` ③ `task-<任务名>/BLUEPRINT-总蓝图.md` ④ **上阶段完成报告的「五、关键偏差」与「十、回写清单」两节** | 3 份 + 上阶段报告 2 节 |
| **写报告的人** | 同「执行阶段的人」+ [BLUEPRINT-回写规范与清单模板.md](BLUEPRINT-回写规范与清单模板.md) | 4 份 |
| **写总蓝图的人** | 规范 §6 + 全部阶段报告的「五、关键偏差」与「十、回写清单」 | 按报告份数 |

**跨目录引用一律用相对路径，不许写裸文件名**（裸文件名换目录后必然断链）：

```
从任务目录指向方法论：  ../methodology/BLUEPRINT-撰写规范.md
从方法论指向任务目录：  ../task-<任务名>/BLUEPRINT-总蓝图.md
同目录内互引：          直接写文件名（如 PHASE-4-完成报告.md）
```

**读取纪律（一句话，写进每份总蓝图抬头）**：

> **不要通读 `methodology/`。** 执行一个阶段只需 **3 份**（规范相关章节 + 总蓝图相关节 + 本阶段蓝图）；
> 经验库**先查场景索引**、命中再展开单条；`BLUEPRINT-经验库-具体坑.md` **按当前技术栈检索，不通读**；
> `BLUEPRINT-经验库-全量台账.md` 只用于追溯某条的原始出处。路径不存在时按本节规则**定位**，不要凭记忆猜。

**验收（本节的检验方式）**：

- 单独把 `methodology/` 拷到另一个任务的同级目录 → 无需改动即可用（跨目录相对路径的写法天然满足）
- 新会话**只读三份**（规范 + 总蓝图 + 本阶段蓝图）能独立执行一个阶段

**可移植性说明（照做即可）**：`methodology/` 里有 **24 处**指向本包范例任务的路径
（形如 `../task-仓库合并/…`：人工台账、范例蓝图/报告、经验出处）。
新任务里只需要**一次全局替换**：

```
../task-仓库合并/     →     ../task-<你的任务名>/
```

替换后所有引用在新目录结构下都可解析（这正是"跨目录相对路径"而不是裸文件名的价值）。
指向 `../2-证据.zip` 的出处路径**不受影响**——它只在核对原始证据时才需要解开。

## §4 施工蓝图必备结构（**12 节**，缺一不可）

```markdown
# Phase N 施工蓝图：<名称>

> **执行者**：agent。本文件自包含，不需要对话历史即可执行。
> **风险等级**：零 / 低 / 中 / 高
> **预计耗时**：N–M 分钟
> **文档规范**：见 `../methodology/BLUEPRINT-撰写规范.md` §4（**跨目录相对路径，不写裸文件名**）
> **前置**：依赖哪个 Phase 的什么产物

> ⚠️ **（可选但推荐）本 Phase 的做法已被实测推翻并替换** —— 若原计划被实测推翻，
> 在标题下方就写清「原计划 / 实测结论 / 新做法 / 证据见第几节」，
> 并明确「执行者请按本文档执行，不要按旧版描述执行」。

## 一、施工目标
   - 核心问题（带 file:line 根因）
   - 目标清单（可勾选）
   - **非目标（明确不做）** ← 防止 agent 过度施工，必须有「为什么」和「何时做」

## 二、实测证据（决定本 Phase 做法，执行前请读）★
   - 支撑本 Phase 决策的**实测数字**，不是推断
   - **被推翻的原计划**：列出试过什么、结果如何、为什么不用它
   - 每条证据标明：在哪测的（沙箱/真机）、怎么复现

## 三、前置条件与停止条件
   - 前置：可执行命令 + 期望值；不满足则**不得开始**
   - ★ **上阶段回写清单无未勾选项**（`grep` 上阶段报告不应命中 `- [ ]`，见 §5.1）
   - 停止：出现什么情况**立即停止并报告**，并写清「为什么必须停」

## 四、改动清单（Agent 直接执行）
   - 逐条：文件路径 + 行号 + 改什么 + 为什么
   - 逐项依据（已实测，非推断）
   - 标注「必改且编译器不会提醒你」的陷阱
   - 顺序敏感的操作要**显式写明顺序及其理由**

## 五、人工环节 ★（人必须做的部分；见 §4.1）
   - H-A 阻塞性拍板（开工前；未答复不得开始 —— 同时登记进 §三 前置条件）
   - H-B 完工评审（本 Phase 的退出条件；人只做判断项，不重算脚本能算的数）
   - H-C 待验项登记（本 Phase 验不了的，登记进 task-<任务名>/HUMAN-人工验证台账.md）
   - 本 Phase 明确**不需要**人做的事（防止让人做无用功）

## 六、验收测试
   - A1…An：每条 → 一条可执行命令 → 期望输出 → **失败处置**
   - 判据必须是**充分的**，不能只是**启发式的**（见 §7.1）
   - 「不算失败」的情形必须提前写明（时点断言、有意保留项、外部增长量）

## 九、已知坑（本 Phase 相关 + 复现情况；从经验库按 H/M/L 检索而来）
```

### 4.1 「人工环节」怎么写（**自 Phase 5 起必备**）

**它解决的现实问题**：被测对象里有**上游不知道其存在**的自建功能（本任务 11 项，官方树 0 命中），
**标准测试结构上抓不到它们的失效**；而且有些决策是**产品取向**，agent 不能替人做。
P0–P4 全自动，**P5 起人回到回路中**。

**三个子节的硬分工**：

| 子节 | 何时 | 性质 | 不满足的后果 |
|---|---|---|---|
| **H-A 拍板** | 施工**前** | **阻塞**：未拿到答复不得开工 | 违规者会做出不可回退的产品决定 |
| **H-B 评审** | 施工**后** | **退出条件**：未通过不得宣告本 Phase 完成 | 人的一次扫视是唯一能发现"功能被顺手删掉"的手段 |
| **H-C 登记** | 施工**后** | 本 Phase 验不了的（构建条件不具备等） | 欠账散落各处 → P8 漏验 |

**四条纪律**：

1. **人只做机器做不了的事**：产品取向、视觉/交互确认、文案可读性。
   **不要让人重算脚本能算的数字** —— 那既浪费人的时间，也会掩盖真正的判断点。
2. **期望值必须由 agent 预先算出**（真实代码在数据副本上跑一遍），不能靠读代码推断、也不能让用户猜。
3. **无法人工验证时必须明说**（例：依赖未装、应用起不来）。
   ⚠️ **不要为了让本节"有内容"而发明无用的人工步骤** —— 让人去点一个跑不起来的程序是负价值。
4. **登记不等于完成**：H-C 的条目是本 Phase 的**欠账**，必须写进交接提示 + HUMAN 台账，
   在具备条件的 Phase（通常是 P8）逐条销账，**未销账不得宣告任务完成**。

**回执要求**：执行者必须把 H-A 的答复**原样抄进**施工记录的 §0（见 §8 子节 0），
H-B 的结论同表登记。**没有回执的人工环节视为未执行。**

> 台账：[../task-仓库合并/HUMAN-人工验证台账.md](../task-仓库合并/HUMAN-人工验证台账.md)（跨 Phase 累积，编号 H-nn，**每任务一份**）。

**「非目标」与「有意保留台账」的区别**（实战验证过的分工）：

| | 非目标 | 有意保留台账 |
|---|---|---|
| 何时写 | 施工**前** | 施工**后** |
| 内容 | 本 Phase 决定**不做**的事 | 施工中确认**故意维持现状**的点 |
| 作用 | 防止 agent 越界施工 | 防止**后续 Phase 重新论证**同一件事 |

两者都要有，不能互相替代。

## §5 完成报告必备结构（**10 节**）

> 骨架取自实战中已收敛的形态（P3/P4 逐节一致）。**报告不是蓝图的复述，是"实际发生了什么"。**
> **v2.2 起为 10 节**：原 9 节 + 新增「**十、回写清单**」（见 §5.1，**未勾完不得提交**）。

```markdown
# Phase N 完成报告：<名称>

> **状态**：✅ 已完成 / ⚠️ 部分完成 / ❌ 失败
> **执行日期**：
> **执行者**：agent（无对话历史，仅凭 [PHASE-N-….md] + [BLUEPRINT-总蓝图.md]）
> **结论**：一句话，含关键数字
> **报告规范**：见 `../methodology/BLUEPRINT-撰写规范.md` §5

## 一、执行摘要
   - 表格：每个验收项 → 结果
   - 「验收总计」：N 项主判据 PASS / FAIL 计数

## 二、最终状态（交接给 P<N+1>）
   - 代码块：关键标识（HEAD / 冲突数 / 快照 / 未提交与否 …）
   - 产出物表格：文件 → 内容 → 规模

## 三、执行过程（含命令与实测输出）
   - 按步骤复述**实际敲的命令**与**实际输出**（不是蓝图里的计划命令）

## 四、验收测试逐项结果
   - 表格：# / 验收项 / 期望 / 实测 / 判定
   - 每项的逐项实测输出（代码块）

## 五、关键偏差与判定修正（**给后续 Phase 必读**）★
   - 逐条：现象 → 根因（实测，非推断）→ 判定 → 对后续的影响
   - **判据本身的修正**也写在这里，并同步进 §7 判据台账

## 六、已知坑的实测复现情况
   - 表格：坑 / 本次是否复现 / 说明
   - **本次新踩到的坑**：单列一节，写明"建议追加进经验库"

## 七、回退方法（已验证可用）
   - 只写**本次实测验证过**的回退路径

## 八、给下一个 Phase 的交接清单
   - 编号清单；🔴 标必读；每条都要能被下一个 Phase 直接消费（路径、命令、判据）

## 九、Phase N 目标达成核对
   - 表格：目标（来自蓝图 §一）→ 状态
   - **非目标遵守情况**：逐条确认没越界

## 十、回写清单 ★（**v2.2 新增；未勾完不得提交**）
   - 四列表：触发条件 / 回写目标 / 回写内容一句话 / 已勾选
   - 四类触发（T1 判据被修正 / T2 基线数值被改写 / T3 蓝图描述被实测推翻 / T4 新增一条经验）
     逐条过一遍；**无触发的写"无"**，不许留空
   - 规则：**只新增 + 标注，不静默删除**；旧值留在原地或移入「历史基线」
```

> 🔴 **自 Phase 5 起，报告还必须给出「人工环节回执」**（可并入 §一 执行摘要与 §三 执行过程）：
> ① H-A 四项决策的**原样答复**；② H-B 每条核对项的结论；③ H-C 已登记进 HUMAN 台账的编号。
> **缺失回执 = 该 Phase 不能判定为完成。**

### 5.1 修正回写（**v2.2 新增，硬要求**）★

**要解决的问题**：修正只活在完成报告里，主蓝图仍是旧口径 → 下一个 Phase **必须回头翻旧报告**才知道该按哪版执行。
一旦有第二份报告，口径就开始互相矛盾。

**四类触发（任一出现即必须回写）**：

| 编号 | 触发条件 | 回写目标 | 回写动作 |
|---|---|---|---|
| **T1** | 判据被修正 | **判据台账**（总蓝图 §7.2 或独立台账） | 追加一行：旧判据 / 新判据 / 依据（哪份报告的哪条偏差）/ 生效范围 |
| **T2** | 基线数值被改写 | 总蓝图「**当前基线**」 | 写新值；**旧值移入「历史基线（仅存档）」**，不删除 |
| **T3** | 蓝图描述被实测推翻 | 总蓝图对应节 | 就地改正 + 保留「**曾错、已修正**」说明（含依据报告） |
| **T4** | 新增一条经验 | 经验库（**按迁移性归位**：H/M → [经验库-通用.md](BLUEPRINT-经验库-通用.md)；L → [经验库-具体坑.md](BLUEPRINT-经验库-具体坑.md)） | 五元组 + 键号续编 + 标明等级 |

**动作要求**：

1. 完成报告末尾必须有「**十、回写清单**」——四列：`触发条件 / 回写目标 / 回写内容一句话 / 已勾选`，
   **未勾选完不得提交**。
2. 下一阶段的前置条件加一条：**上阶段回写清单无未勾选项**
   （验证：`grep -n "^\s*- \[ \]" task-<任务名>/PHASE-<上阶段>-完成报告.md` → **应无输出**）。
3. **回写只「新增 + 标注」，不静默删除**：旧值留在原地，或移入「历史基线」段落。

> 完整定义、话术与可直接抄的清单模板见 **[BLUEPRINT-回写规范与清单模板.md](BLUEPRINT-回写规范与清单模板.md)**。

**验收（本节的检验方式）**：

- 新会话**只读「规范 + 总蓝图 + 本阶段蓝图」即可正确执行** —— 不需要回头读任何旧阶段报告来纠正口径
- 若发现"必须翻旧报告才对"，说明有一条回写漏了：补回写，而不是在报告里加导航

## §6 总蓝图的职责与同步义务

总蓝图 = **索引 + 全局约束 + 已拍板决策 + 当前基线**。它不含具体步骤。

必备内容：

| 区块 | 内容 |
|---|---|
| 任务背景 | 一句话 + 关键拓扑（决定策略，不可搞错） |
| 成功判据 | Definition of Done，逐条可验 |
| 全局约束 | 工具边界 / 环境陷阱 / 每步可验证 / 提交粒度 |
| Phase 索引 | 表格：Phase / 名称 / 性质 / 风险 / 状态 / 文档链接 |
| 依赖关系 | 为什么不可跳过（硬依赖理由） |
| **已拍板决策** | 「Agent 不得重新论证」的决策表 + 依据文档 |
| 必须保护的东西 | 基线文件 + 逐项清单（标准测试覆盖不到的部分） |
| 参考文档索引 | 本目录（`task-<任务名>/`）+ **方法论目录**（`../methodology/`：规范、经验库、回写规范、模板），全部用**跨目录相对路径** |
| **当前基线** | ✅ 最新，供逐项比对；历史基线折叠为"仅存档" |
| 回退手册 | 分级回退命令 |

### 同步义务（硬要求）

- 每个 Phase 收到的是**总蓝图 + 该 Phase 蓝图**两个文件 → 总蓝图里的错误会**污染每一个 Phase**
- 因此：**实现过程中发现总蓝图需要修改时，必须回写总蓝图**（触发条件与动作见 §5.1 的 T1–T4）
- 总蓝图必须标出**它自己错过的地方**（例：`> ⚠️ 本节曾有两处错误，已修正`）——这是可信度的一部分，不是丢脸
- 总蓝图的「当前基线」被新 Phase 取代时，旧值**移入"历史基线（仅存档）"**，不要直接删
- **总蓝图抬头必须写一句读取纪律**：不要通读 `methodology/`；按 §3.3 的最小必读集读

## §7 判据台账（判据会错，且必须留痕）★

### 7.1 充分判据 vs 启发式指标

写验收项时必须自问：**这条命令真能证明我想证明的事吗？**

| 类型 | 例子 | 判定力 | 要求 |
|---|---|---|---|
| **充分判据** | 退出码为 0、`JSON.parse` 成功、`diff` 为 0 行、目标 id 命中数 = 0 | 强 | 直接可用 |
| **启发式指标** | `Select-String` 命中数 ≥ 1、`findstr` 命中文件数 ≥ 基线 | **弱**（计数不证明内容正确；只删文件不算逻辑也会让计数退化） | **必须配一条交叉验证**，或明确标注为"代理指标" |

> 实战教训：某个 `grep "qq:<id>"` 的判据**结构上抓不到**某类残留（向量条目里存的是**裸** id，
> 没有渠道前缀）。判据的形状决定了它能看见什么——写的时候就要想清楚这一点。

### 7.2 判据台账格式（跨 Phase 累积）

判据一旦被修正，必须在两处留痕：**完成报告 §五** + **总蓝图或独立台账**（编号累积）。

| 编号 | 旧判据 | 新判据 | 依据（哪个 Phase 的哪条偏差） | 生效范围 |
|---|---|---|---|---|
| J-01 | 未跟踪文件数 ≥ 141 | 逐项核对工作资产是否仍在磁盘上 | P3 偏差 2（判据与步骤自相矛盾） | P3 之后 |
| J-02 | 其余 10 项功能基线不得退化 | 退化必须能归因到本 Phase 主动删除的文件 | P4 偏差 3（删文件必然让"仅存在于被删文件"的标识退化） | P4 之后 |
| J-03 | grep 出的每一处 `<id>` 都落在 `subjectIds` 里 | 同上，但 **`memory-trace.log` 例外**（它是删除动作的审计载体） | 手工验证第 6② 条 | 该任务之后 |

**必须写成台账的理由**：修正散落在各份完成报告里，后续 Phase 得翻遍所有报告才知道该按哪版验收。

> **人工验证的欠账用同级台账累积**：[../task-仓库合并/HUMAN-人工验证台账.md](../task-仓库合并/HUMAN-人工验证台账.md)（编号 **H-nn**，自 P5 起生效）。
> 判据台账管"**按哪版验收**"，人工台账管"**还欠哪些人要做的事**"。两者都要有。
> **各任务自己的一份**：台账属任务专属，新任务在 `task-<任务名>/` 下另起一份，不要复用别人的欠账清单。

### 7.3 三类必须提前写明的"不算失败"

1. **时点断言**：擦除后主体又活动了 → 断言自然失败。判据要写"取值于**动作刚完成的那一刻**"
2. **有意保留项**：预先声明保留的东西出现在扫描结果里，不算残留
3. **外部增长量**：别的进程在写（语料、审计行数）→ 给容差，或改成"只允许纯追加"的相对判据

## §8 施工记录（执行者追加的 §12）

> **原则**：遇到真实代码与蓝图冲突时，**以真实代码为准**。
> 本节由施工方在完成后追加，记录**与蓝图不一致处**及原因。

必备子节（按需增减，但 1/2/4/5 为必需）：

| 子节 | 内容 | 格式 |
|---|---|---|
| **0 人工环节回执**（**Phase 5 起必需**） | H-A 决策答复（原样抄录）+ H-B 核对结论 + H-C 登记确认 | 三张表，见 [../task-仓库合并/PHASE-5-移植适配.md](../task-仓库合并/PHASE-5-移植适配.md) §十二 |
| **1 主进程 / 实际落地** | 逐条记录偏离 | 三列表：**蓝图 / 实际实现 / 原因** |
| **2 蓝图未覆盖、施工中发现的漏洞** | 蓝图漏掉的，一并修复 | 三列表：**位置 / 问题 / 修复** |
| 3 蓝图最大不确定点的核实结论 | 蓝图自己标注的疑问，施工后给答案 | 引原文 + 结论 + 证据 |
| **4 有意保留的"不处理"点** | 故意维持现状的，附理由 | 清单，每条给"为什么不管" |
| **5 验收（实测数字）** | 门禁命令 + 实测值 | 表格：命令 / 结果 |
| 6 验收后修复 | 交付后才发现的，单开一节 | 现象 / 根因 / 修复 / 复验 |
| 7 经验追加 | 新坑 + 判据修正 | 见 §9，按 H/M/L 归位到经验库 |
| 8 待做 / 未做 | 如实列出，不给"已完成"的印象 | 表格：项 / 状态 / 说明 |

### 8.1 缺陷编号体系

发现的问题按 **D1、D2、D3…** 编号（观察类用 **O1、O2…**），每条必须给：

```
现象（什么命令/什么操作 → 观测到什么，带真实数字）
根因（机制层，不是"不小心"）
影响（谁会受害、多严重、会不会自愈）
修复口径（谁拍的板、按什么口径）
修复（改了哪些文件、判据是什么）
复现/证明证据（能独立复核的脚本或断言编号）
为什么以前没被发现（这一条最有价值——它决定同类问题还有多少）
```

> **「为什么以前没被发现」是必填项**。它直接回答"还有多少同类问题没暴露"。

### 8.2 手工验证记录

手工验证（需真人操作）必须留证，格式：

| 步骤 | 期望（权威来源） | 实测 | 判定 |
|---|---|---|---|

- **期望值必须由"真实代码在数据副本上跑一遍"产出**，不能靠读代码推断
- 每个"不算失败"的情形提前写明
- 差异必须归因到**具体哪一侧错了**——包括**验证工具自己错了**（见经验库 通用库 C14「验证工具自身必须被验证」）

## §9 经验库的用法与追加义务

**经验库分三级、按迁移性拆两库**（详见 [BLUEPRINT-经验库-通用.md](BLUEPRINT-经验库-通用.md) 开头的分级表）：

| 等级 | 判据 | 放哪 | 怎么读 |
|---|---|---|---|
| **H** 换语言/框架仍成立 | 「换一种语言还成立吗？」→ 是 | `BLUEPRINT-经验库-通用.md` | 写蓝图前**必读** |
| **M** 换同类系统仍成立 | 「换同类框架还成立吗？」→ 是（否 → L） | `BLUEPRINT-经验库-通用.md` | 写蓝图前**必读** |
| **L** 绑定具体命令/API | 「核心是命令/API 行为吗？」→ 是 | `BLUEPRINT-经验库-具体坑.md` | **按当前技术栈检索，不通读** |

全量溯源用 [BLUEPRINT-经验库-全量台账.md](BLUEPRINT-经验库-全量台账.md)（186 条 R + 10 条 X，带 `文件:行号` 出处）。

使用规则：

1. **写蓝图前先查一遍**：通用库（H/M）整份过一遍；具体坑库**只查当前技术栈那一章**
2. 蓝图「九、已知坑」写**与本 Phase 相关**的条目 + 本次复现情况，不必复述全库
3. **每次施工发现新坑，必须追加进经验库**（不是只写进完成报告），**按迁移性归位**到通用库或具体坑库
4. 每条经验必须是**五元组**，缺一不可，并标明等级（H/M/L）：

```
错误做法 → 症状（含原样错误信息）→ 根因（机制层）→ 正确做法（可执行）→ 出处（文件:行号）
```

5. **经验的价值排序**（越靠前越珍贵）：
   - ① **被实测推翻的原计划**（"我们本来打算…，实测证明零收益"）
   - ② **判据自身的缺陷**（"这条断言结构上抓不到它"）
   - ③ **验证工具的缺陷**（"我的沙箱漏拷了一个文件，差点误判成产品缺陷"）
   - ④ 环境与命令坑（`2>&1`、编码、非 ASCII 路径…）

> ⚠️ **不要把具体结论当通用知识套用**：L 级条目里的命令与 API 结论**只在那套技术栈成立**。
> 换栈后要重新验证，不能照搬（这也是拆成两库的原因）。
