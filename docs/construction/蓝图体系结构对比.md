## 一、两个目录的定位差异

| 维度 | `docs/merge-plan/`（规范格式） | `docs/construction/SELF-update 260925/`（实战形态） |
|---|---|---|
| 文档数 | 17 | 8 |
| 总行数 | 约 5,700 | 约 8,800 |
| 主导文档类型 | 施工蓝图 + 完成报告 + 总蓝图 + 决策文档 | 施工方案（含 §9 施工记录）+ 跨阶段总览 + 手工验证记录 |
| 命名族 | `BLUEPRINT-*` / `PHASE-N-<主题>` / `PHASE-N-完成报告` / `NN-<主题>` | `phase<N>-<主题>` |
| 骨架 | **固定 7 节**（总蓝图 §七 规定） | **随复杂度生长**（§9 子节数 0 → 6） |

**关键事实**：`merge-plan` 的 7 节模板**只覆盖"施工蓝图"一种文档**，对完成报告没有任何格式规定；
而 `construction` 里的文档在实战中自然演化出了更丰富的骨架，**两者之间没有任何指针相连**。

## 二、施工蓝图骨架对比

`merge-plan` 的强制模板（`BLUEPRINT-总蓝图.md` §七 原文，7 节）：

```
一、施工目标        二、前置条件与停止条件   三、改动清单
四、验收测试        五、产出物清单          六、回退方法        七、已知坑
```

`merge-plan` 最完整的一份实际蓝图（`PHASE-5-移植适配.md`，501 行）已长出 **9 节**：

| # | 章节 | 是否在模板里 |
|---|---|---|
| 一 | 施工目标（含"核心问题 / 分配依据（实测）/ 目标 / 非目标"四小节） | ✅ |
| 二 | 前置条件与停止条件 | ✅ |
| 三 | 改动清单 | ✅ |
| 四 | 验收测试（A1–A7） | ✅ |
| 五 | **归属修正说明（执行者必读）** | ❌ 模板外 |
| 六 | 产出物清单 | ✅ |
| 七 | 回退方法 | ✅ |
| 八 | 已知坑 | ✅ |
| 九 | **给 P6 的交接提示** | ❌ 模板外 |

`PHASE-2-合并配置对齐.md`（286 行）还多出一节**「二、实测证据（决定本 Phase 做法，执行前请读）」**，
且该节被文档自己引用（「证据见第二节」「见第二节证据 3」）——**这一节在模板里根本不存在**。

### 该节的存在理由（原文）

| 做法（均开 `merge.renormalize`） | 冲突文件 |
|---|---|
| 无 `.gitattributes` | **46** |
| 有 `.gitattributes`（`* text=auto eol=lf`） | **46** |

**差异 = 0。** → 这一行就是"不做 `.gitattributes`"这个**非目标**的全部依据。

`PHASE-2` 还在标题下方加了置顶区块：

> ⚠️ **本 Phase 的做法已被实测推翻并替换（与原计划不同）**
> 原计划：加 `.gitattributes` + `git add --renormalize .`（会改动 57 个文件的索引）
> 实测结论：那套做法**没有收益**（冲突数一个都不减），却要动 57 个文件
> **执行者请按本文档执行，不要按旧版的 P2 描述执行。**

**结论**：`实测证据`（含被推翻的原计划）在实战中是**一等公民**，但不在模板里。

**第三份最值得注意**：`phase3-person-memory-overview.md` **不是总蓝图，是"总览"**——
它把 §4「跨阶段关键约束」写成了一等公民，9 条（`4.1`–`4.9`）每条都是"现在就必须知道，否则到后面会推倒重来"：

> `4.1` assistant 消息的时序问题 · `4.3` 私聊 transcript 没有 `speakerId` ·
> `4.4` 压缩总结会混合多人 · `4.8` L2 记忆不进主聊天 prompt，但串记忆问题依然存在——**它换了扇门**

`merge-plan` 总蓝图的「全局约束」是**工具/环境类**（只读优先、非 ASCII 文件名、命令规范），
而这一份是**领域语义类**（时序、缺字段、结构混合）。**两者是两种约束，不是同一种的深浅版本。**
