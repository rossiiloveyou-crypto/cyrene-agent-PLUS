## 一、你的两个旁听，性质根本不同

| 目的 | 收集"真人怎么说话"，为自学习准备 |

## 二、★ 你的语料文件自己写明了为什么**不能**并进 CTA 轨迹

这是本轮最重要的发现。`src/main/corpus/group-corpus.ts:20-28` 的原文注释：

> `channels/history/` 和 `channels/archive/` 都在 `MEMORY_TARGETS` 里，
> 用户点「清空记忆」会被整目录 `rmSync`；`history` 热文件还会在超过
> **200 行**时截断（老行搬去 archive）。而这个语料是**只增不减的长期资产**，
> **被清空就等于前功尽弃**。
>
> 所以它放在 userData **顶层** `group-corpus/`，与 `channels/` 平级 ——
> **不在任何 `MEMORY_TARGETS` 条目的路径内，物理上不可能被记忆清理误伤**；
> 同时登记在 `MEMORY_PRESERVED` 里，并有回归测试锁住这条边界
> （见 `memory-deletion.test.ts` 与 `group-corpus-isolation.test.ts`）。

**你已经亲手写下并测试锁定了这条架构边界。** 翻译成一句话：

> 语料必须活在一个**不会被清空、不会被截断**的地方，因为它是训练资产。

而 CTA 轨迹**恰恰是被设计成会截断和归档的** —— 它有 token 预算驱动的压缩（compactor）
和 `segments/` 归档。**把语料迁进轨迹 = 亲手拆掉你自己建的那道防线。**

### 如果强行迁移，会丢掉什么

| 损失 | 说明 |
|---|---|
| `MEMORY_PRESERVED` 保护失效 | 语料变成"记忆"的一部分，用户点清空就被删 |
| 压缩会吃掉语料 | 轨迹的 compactor 按 token 预算裁剪，语料会被逐步压掉 |
| 两个现有回归测试失效 | `memory-deletion.test.ts` + `group-corpus-isolation.test.ts` 锁的边界被破坏 |
| 全量性丢失 | 语料的价值在"全量"，一旦受 token 预算约束就不再是全量 |
| 按天分文件 / 跨群查询能力 | 语料的目录结构支持 `corpusStats()` 统计与按群训练；轨迹是按会话组织的 |

## 三、修订后的建议（与我上一轮不同）

### ❌ 修订掉：不要为了"统一存储"把语料迁进 CTA

我上一轮说"方案 3 等于正式承认两套存储" —— 这句话在**语料**这件事上是**错的**。
**两套存储是正确设计，不是技术债。** 它们的生命周期、保留策略、隐私语义完全不同：

| | 上下文旁听（A） | 自学习语料（B） |
|---|---|---|
| 保留 | 短窗口 + 归档 | 全量永久 |
| 可被用户清空 | **是**（属记忆） | **否**（刻意豁免） |
| 可被压缩裁剪 | 可以 | **绝不可以** |
| 与模型上下文耦合 | 强耦合 | **零耦合**（从不进 prompt） |

### ✅ 修订为：旁听 A 用**方案 1**，旁听 B **原地不动**

你说了两件事，它们共同解锁方案 1：

1. **向前兼容不慌** —— "我的更新设计出来就是为了新版本的，旧版本默认放弃支持，readme 里加警告即可"
   → 方案 1 的唯一实质风险（旧版本读不了轨迹）**已被你主动接受**
2. **只要功能性不受影响**

于是方案 1 现在是最优解：

| 为什么方案 1 现在更好 | 说明 |
|---|---|
| 架构上是"归位" | 旁听 A 本质就是**一条没触发昔涟的对话条目** → 天然属于轨迹 |
| 官方设计本就容纳 | 两个 reducer 对未知类型显式忽略（`projection.ts:145-148`、`:605-606`），无需改 reducer 就能安全落盘 |
| 有现成先例可抄 | 官方 `interruptionNotesWithSources`（`:299-338`）就是"按类型选择性注入内部注记"的范式 |
| 需要时可被压缩 | 与它的短期窗口语义一致 |
| 用户清空记忆时行为一致 | 轨迹与 `channels/` 同属记忆范畴，语义统一 |

**方案 3 现在的定位**：降级为"如果方案 1 落地受阻时的备选"，不再是首选。

### ⚠️ 陷阱 1：第 2、3 项漏任何一个，该对话的每次读取都抛 `TRANSCRIPT_CORRUPT_ROW`

因为 `validateLoadedTranscriptEntry` 是 **fail-closed**，且被 7 个调用点覆盖
（追加、快照、JSONL 热行回放、一致性断言、归档段回放）。
**而全代码库没有任何 `assertNever` 穷尽性守卫 → 类型层完全干净 → 编译器不会提醒你。**

**必须补一个全链路往返测试**：追加 → 读取 → 快照 → 压缩 → 归档。
这是唯一能兜住漏改白名单的手段。

### ⚠️ 陷阱 2：`refreshProjection` 会随每次旁听追加触发

`conversation-journal-service.ts` 在 `:140,160,171,215,236` 都有 `await this.refreshProjection(...)`。
群聊旁听是**高频**路径（群里每条消息都可能是一条旁听），
所以这里需要**批量/节流**，不能每条消息都重建一次投影。

> 这一项官方没有先例（官方的 `appendUser` 是低频的触发路径），需要你自己的设计。
> 你的 `history-log.ts` 已经有现成的节流先例可参考（`OBSERVATION_WRITE_INTERVAL_MS`）。

## 五、向前兼容的落地方式（你已接受，这里给个具体做法）

你说"readme 里加警告就好"。为了让警告有效而不是空话，建议：

1. **README 写清楚**：本版本起，渠道对话轨迹包含新条目类型；
   **回退到旧版本会导致这些对话历史无法打开**（旧版本会报 `TRANSCRIPT_CORRUPT_ROW`）。
2. **在 release notes / 更新说明里重复一次**（用户不一定读 README）。
3. 若日后想减轻这个代价，有一条不破坏现有数据的中期路径：
   给 store 的校验器加一个**"未知类型跳过并记录警告"**的软降级分支 ——
   但这会削弱 fail-closed 的完整性保护，属于独立权衡，不建议与本次合并混做。
