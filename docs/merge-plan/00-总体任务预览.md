## 四、三个真正的难点（也是"不算太难"这个判断需要修正的地方）

### 难点 1：行尾字符不匹配 —— 会让 diff 膨胀 475 倍

两个仓库都用 `autocrlf`，但**入库行尾不同**（官方 CRLF、你 LF），同一个文件被当成两个不同文件。

实测：

| 文件 | 表面 diff | 真实差异 | 膨胀 |
|---|---|---|---|
| `tool-registry.ts` | 475 + 475 − | **1 + 1 −** | **475×** |
| `memory-user-ipc.ts` | 436 + 435 − | 9 + 8 − | 48× |
| `token-usage-store.ts` | 306 + 290 − | 18 + 2 − | 17× |

**这不是"难"，是"必须先扫干净地"** —— 否则你和 agent 都会被几百行假冲突淹没，做出错误判断。
对策：合并前加 `.gitattributes` 统一行尾，之后一律用 `git merge -X renormalize`。一步就能消掉 4 个假冲突文件。

### 难点 2：15 个"作者删了、你还在改"的文件

这是最需要**判断**的地方，没有机械答案。逐个分析后大致分三类：

| 处置 | 数量 | 例子 |
|---|---|---|
| **跟着删**（官方已 React 化，你的改动落在死路上） | 13 | 旧设置窗口三件套、旧侧栏、`useChatAppearance` |
| **必须恢复官方版**（官方有活引用者，删了会编译失败） | 2 | `settings/api/presets.ts`（3 个 importer）、`tokens/panel.ts`（1 个） |
| **抽取精华后删** | 1 | `chat-appearance.ts` → 你只有 3 个导出值得留（`USAGE_BADGE_*`） |

### 难点 3：核心三文件是"架构不兼容"，不是文本冲突

`dispatcher.ts` / `bootstrap.ts` / `channel-context.ts` 这 3 个文件 + 3 个测试：

| | 你的方案 | 作者的方案 |
|---|---|---|
| 历史归谁管 | 渠道自己管 | journal 唯一权威 |
| 给 AI 的输入 | 位置参数（4 个） | 对象（带 modelContext / sink / runId） |
| 上下文怎么来 | `buildOptions({messages})` | `modelContext` + 失败即关 |

**这 6 个文件不能"合并"，只能"按新结构重写、把你的功能挂上去"。**
这是整个任务里唯一称得上"硬骨头"的部分，也是 agent 最需要人工复核的地方。

## 五、分阶段目标预览（9 个阶段）

每个阶段：**改什么** → **为什么** → **影响** → **产出**。

---

### Phase 0 · 备份与回退锚点 🛡️

- **改什么**：不改代码。把你 135 个未跟踪文件 + 144 个改动**固化成一个 git 提交**，打上标签；再做一个物理目录备份。
- **为什么**：你的仓库 reflog 只有 1 条克隆记录，**没有任何回退网**。未提交工作一旦被覆盖就永久丢失，且没有任何补丁包含那 135 个新文件。
- **影响**：零风险，纯增量。你的工作目录内容不变，只是多了一个"存档点"。
- **产出**：一个像 `pre-merge-backup` 这样的标签 + 一份物理备份 + 一份"合并前状态清单"。
- **⚠️ 关键**：不能用逐文件脚本复制（有中文文件名会静默丢失），必须用 git 自己的机制。

### Phase 1 · 工具链对齐 🔧

- **改什么**：装 Node 24 + npm 11。**不动代码**。
- **为什么**：项目要求 `node >=24 <25`，你本机是 **v22.23.2 / npm 10.9.8**；官方的依赖锁文件是用 npm 11.16 生成的。版本不对会导致 `npm ci` 报错并生成与官方分歧的锁文件。
- **影响**：只影响你的开发环境。装完 Node 24 后旧项目仍可跑（多版本共存）。
- **产出**：`node -v` 显示 24.x，`npm -v` 显示 11.x。
- **为什么单独成阶段**：后面所有验证（tsc / vitest / build）都依赖它。**没有它，合并完无法证明代码能跑。**

### Phase 2 · 行尾统一（扫干净地）🧹

- **改什么**：新增 `.gitattributes` 声明统一行尾，然后 `git add --renormalize .` 单独提交一次。
- **为什么**：消除难点 1 的 475 倍 diff 膨胀，让所有后续冲突都是"真冲突"。
- **影响**：会产生一个"看起来很大但全是行尾"的提交 —— 这是**预期的、正常的**，不是代码改动。之后所有 diff 都可读。
- **产出**：`git diff --stat` 不再出现整文件重写的假象；实测可消掉 4 个假冲突文件。

### Phase 3 · 执行合并（在沙箱里做）🔀

- **改什么**：`git merge -X renormalize b11b8851`，产生 46 个冲突的合并状态。
- **为什么**：这是"分水岭"动作 —— 一次性拿到官方 862 个文件的新版本 + 你的 135 个新文件，把剩余工作量收敛成一份明确清单。
- **影响**：工作区会被大规模改写。**必须在 Phase 0 完成之后做，且先在沙箱做一遍。**
- **产出**：`70-merge-worklist.txt`（46 个冲突文件清单）+ 862 个文件已就位。
- **实测结论**：这一步**你 95% 的工作已经自动保住了** —— 862 个文件自动合并，你的新文件零冲突。

### Phase 4 · 直接套用（省力阶段）📦

- **改什么**：把 46 个冲突里的 **15 个"A 类"** 一次处理掉 —— 13 个跟着官方删、2 个恢复官方版；以及确认 135 个新文件完好。
- **为什么**：这 15 个是"作者已经拆除的房间"，逐个纠结没有价值。判据很硬：**官方树里还有没有 importer**。
- **影响**：你的**未跟踪新模块完全不受影响**（记忆、区块、语料、审计、白名单全部原样保留）。
- **产出**：冲突数从 46 降到 ~31。

### Phase 5 · 移植适配（把功能搬进新家）🏗️

- **改什么**：
  1. 把 `chat-appearance.ts` 里你独有的 3 个导出（`USAGE_BADGE_*`）抽成独立小模块，然后放手让旧文件被删；
  2. 你的 28 个新 IPC 通道并入官方 `ipc-channels.ts`，同时删掉官方已废弃的 `CHAT_TYPOGRAPHY_CHANGED` 及其 3 处引用；
  3. i18n 的 537 个键**按 key 合并**进官方 `react/i18n`（不要按 hunk 合，会错乱）；
  4. 你的设置项（groupContextLimit、zones、记忆面板、关键词导入）落到官方 React 设置页；
  5. `settings-store.ts` 里你的 toolAccess/keywords/audit 折进官方的新结构。
- **为什么**：你的**功能**都要活，但**旧界面容器**已经不存在了，必须换容器。
- **影响**：这是**工作量最大**的一个阶段，但性质是"搬运"而非"发明"，风险可控。
- **产出**：设置页里你所有功能可见可用；i18n 文案完整。

### Phase 6 · 核心三文件重写（唯一硬骨头）💀

- **改什么**：`dispatcher.ts`、`bootstrap.ts`、`channel-context.ts` + 对应 3 个测试，按官方 journal 结构重写，把你的功能挂回去。
- **为什么**：难点 3 所述 —— 架构不兼容，只能重写。
- **影响**：**这是全局风险最高的阶段。** 两个务必：
  - `interceptByKeyword` + 审计要放在**重放去重之后、限流之前**（否则重投消息会重复写审计；被拦截消息不该消耗额度）；
  - 必须**补一个集成测试**断言 dispatcher 真的写了 history —— 否则群聊旁听会静默消失而测试全绿。
- **产出**：渠道链路在官方新架构上跑通，且你的审计/关键词/群上下文功能存活。

### Phase 7 · 边界编译修复与构建链切换（收尾）🔨

- **改什么**：
  1. 修复跨模块类型断裂（`build-options`、`agent-runtime`、`tool-registry`、`settings-facade` 等约 10 个文件）；
  2. **删除 `vite.config.ts`**，把里面你写的 `host: "127.0.0.1"` + `strictPort: true` 抢搬到官方 `vite.config.mts`；
  3. 取官方 `tsconfig.json` + `tsconfig.renderer.json`；
  4. 取官方 `package.json` + 锁文件，重贴你的版本号。
- **为什么**：`vite.config.ts` 会**静默遮蔽** `vite.config.mts`（Vite 取第一个匹配就停，**不报警告**）—— 不删它，构建会静默用旧配置，症状诡异且难查。
- **影响**：构建链切到官方 Vite 8；你那个 `host` 修复是真实 bug 修复，**必须抢救**（不搬会导致 Electron 启动 `ERR_CONNECTION_REFUSED`）。
- **产出**：`npm run build` 与 `build:renderer` 能跑通。

### Phase 8 · 合并后验证与冒烟测试 ✅

- **改什么**：不改代码。`npm ci` 重装 → `tsc` 类型检查 → 跑测试 → 手工冒烟。
- **为什么**：**合并"看起来完成"和"真的能用"之间隔着一整轮验证。**
- **影响**：这一步会暴露前面所有阶段的遗漏。预期会有 Vitest 5 的 `clearMocks` 余波（需要重新生成 2 个快照）。
- **冒烟重点**（你点名要保的东西）：记忆管理能开、区块能建、控制台能看、审计有记录、渠道能收消息。
- **产出**：验证报告 + 已知问题清单。

### Phase 9 · 回落与加固 🔒

- **改什么**：写清"哪些你的改动被有意放弃、为什么"；建立上游同步机制（定期 `git fetch` 官方 + 增量比对脚本）。
- **为什么**：这次冲突的**根因是你 12 天没有同步**。不解决流程，下次还会有同样的问题，而且会更痛。
- **影响**：纯文档与流程，无代码风险。
- **产出**：变更日志 + 同步 SOP。

## 七、需要你拍板的两件事

这两个决定**不能让执行者替你选**，因为它们是产品取舍：

### 决策 1：桌面对话绑定功能，保留还是删除？

- **你的做法**：已删除 `conversation-binding-api.ts` 及相关 UI（认为"渠道会话自带上下文，不再绑定桌面对话"）。
- **作者的做法**：保留它，并把它当作 journal 的写入目标（`boundConversationId`）。
- **有意思的地方**：作者**独立地**也清掉了同一批"绑定镜像"路径 —— 说明**你的方向跟作者是一致的**，只是他保留了最后的写入目标。
- **我的建议**：**本次保留官方语义**。理由：保留的成本几乎为零（什么都不用改），而"不绑定"的行为依然可达（就是不设绑定即可）。删除它反而要连带改 5 处以上，收益为零。
- **代价**：多留一个你暂时不用的模块。

### 决策 2：旧设置窗口要不要保？

- **背景**：作者删了整个旧设置窗口，改 React。
- **选项 A（推荐）**：**跟官方走 React**。你的功能搬进 React 设置页。代价是 Phase 5 工作量最大；好处是以后不再跟官方对抗。
- **选项 B**：把旧设置窗口救回来（恢复构建入口 + 窗口工厂）。短期省事，但它是一个官方已判死刑的文件，**以后每次同步都要再打一次架**。
- **我的建议**：选 A。你的核心诉求是"记忆/区块/控制台不要动" —— 选 A 这些功能**全部保留**，只是换个地方显示。
