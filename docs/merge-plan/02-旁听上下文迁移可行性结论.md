# 02 · 群聊旁听上下文：迁移到 CTA 的可行性结论

> 本文回答 `01-已拍板决策与技术修正.md` 里唯一挂起的技术未知项。
> 方法：对官方 `b11b8851` 的 CTA 轨迹系统做了逐文件、逐行核查（含两个 reducer、store 校验器、压缩器、归档器、全部测试）。
> 结论可信度高，但**有一个必须由你拍板的代价**。

---

## 一、一句话结论

**可行，而且投影层天然安全** —— 但**代价不在工作量上，在"向前兼容"上**。

好消息比预期多：官方的架构**本来就是为这件事设计的**
（投影对未知类型默认忽略、笔记注入是按类型选择性开启、压缩与归档完全类型无关）。
坏消息是：**一旦写入新类型，任何旧版本程序打开这段对话都会硬失败。**

---

## 二、先回答那个决定性问题：投影是"遍历全部"还是"只挑特定"？

**答：它遍历全部条目，但只为特定类型生成消息节点。其余全部落进显式的 `default: break`。**

两处 reducer 都有**显式的忽略未知分支**：

`conversation-transcript-projection.ts:145-148`（模型路径）
```ts
      default:
        // Presentation, receipts, interruption, backfill and checkpoints do
        // not themselves alter the active canonical node sequence.
        break;
```

`conversation-transcript-projection.ts:605-606`（界面路径）
```ts
      default:
        break;
```

**这意味着**：新增一个类型后，
- 它会被**持久化**（进 `seq`、进快照、进归档）
- 但**对 `buildModelContext()` 完全不可见**，直到你**主动**加一个分支
- **不会报错、不会崩、不会有编译错误**

> 这正是你希望的"天然安全默认值"。
> 附带一个重要事实：**全代码库没有任何 `assertNever` 穷尽性守卫** ——
> 所以新增联合类型成员**不会产生任何 TypeScript 编译错误**，编译器不会帮你发现问题。

---

## 三、真正的阻塞点：store 是"失败即关"的白名单（两个必改点，编译器不会提醒你）

`conversation-transcript-store.ts` 里有**两处**硬编码的类型白名单，都是 fail-closed：

**第一处 —— 白名单 Set（`:702-706`）**
```ts
  const kinds = new Set([ ...10 个已知类型... ]);
  if ( ... || !kinds.has(candidate.kind as string) || ... )
    throw new Error("TRANSCRIPT_CORRUPT_ROW");
```

**第二处 —— payload 校验的 `default` 分支（`:730-785`，`:782-783`）**
```ts
    default: return false;
```

**这两个校验器被 7 个地方调用**，覆盖：追加、快照、JSONL 热行回放、一致性断言、归档段回放。
所以：**只改一处 = 该对话的每一次读取都抛 `TRANSCRIPT_CORRUPT_ROW`。**

**⚠️ 最危险的地方**：漏改时**编译器完全不报错**（因为类型层没问题），
只会在运行时炸。必须专门写一个"追加 → 读取 → 快照 → 压缩 → 归档"全链路往返测试来兜住。

**没有"跳过未知类型"的逃生通道。** 归档路径会把同样的失败转成
`TRANSCRIPT_ARCHIVE_CORRUPT_ACTIVE` / `TRANSCRIPT_ARCHIVE_CORRUPT_SEGMENT`。

## 四、★ 必须让你拍板的代价：向前兼容性

这是整个分析里**唯一真正的风险**，而且它不是技术实现问题，是产品问题。

**事实**：轨迹条目的类型集合**没有任何版本号**。
版本号只存在于快照层（`TranscriptSnapshot.schemaVersion = 1/2`），**管不到条目类型**。

**后果**：

```
你今天用新版本写了一条「旁听」记录
        ↓
明天你回退到旧版本（或用户拒绝升级、或装了旧版安装包）
        ↓
旧版本读这段对话 → TRANSCRIPT_CORRUPT_ROW → 这段对话历史打不开
```

**没有降级逃生通道**：不存在"跳过未知类型"的分支，也没有版本开关可以绕。

**为什么这对你特别重要**：这是一个 Electron 桌面应用，
「用户装旧版」「更新失败回滚」「多机版本不一致」都是现实场景。
一旦写入就无法回撤。

**缓解手段（若选方案 1）**：用一个能力开关控制是否写入旁听记录 —— 但开关只能防"新写"，防不了"已写"。

### 方案 3 的两个确切接入点

`modelContext` 是一个普通局部对象，是完美的接缝：

```
src/main/channels/dispatcher.ts
  :244   const modelContext = await journal.buildModelContext(target.conversationId);
  :256   modelContext,          ← 在这里合并旁听摘要

src/main/agui-bridge.ts
  :539   modelContext = await journal.buildModelContext(sessionId);
  :568   modelContext,          ← 桌面路径若也需要，同一手法
```

类型是 `MaterializedTranscript { messages; uncertainEffects; throughSeq }`，
往 `.messages` 推一条 `role:"system", visibility:"internal"` 的消息是**类型正确且有先例的** ——
官方投影自己就在 `:268-284` 注入完全相同的内部注记。

**代价**：你的 `history-log.ts` 旁挂存储继续存在，等于**正式承认有两套存储**。
但你说过"只要功能性不受影响" —— 这个方案功能上零损失、风险最低、随时可撤。

## 六、我的建议

**分两步走，先方案 3，后方案 1（可选）。**

### 第一步（本次合并）：用方案 3

理由：
1. **零 schema 风险** —— 不可能污染轨迹协议，不可能触发 fail-closed
2. **无向前兼容隐患** —— 不落新数据，随时可回退
3. **改动面 1–2 个文件**，而不是跨 4 个模块
4. 你的 `history-log.ts`（598 行、含月度归档 + 按人擦除）**继续服役**，这些能力官方**本来就没有**
5. 只换"摘要注入点"，不换"记录存储" → **功能完全不受影响**，符合你的唯一要求

### 第二步（本次合并之后，作为独立的、深思熟虑的改动）：可选方案 1

如果你希望真正收敛到单一存储，方案 1 在架构上是**可行且被官方设计容纳的**。
但请把它当成一次**独立的功能变更**来做，因为：
- 需要专门的全链路往返测试兜住"漏改白名单"的陷阱
- 需要先接受或缓解"旧版本读不了这段对话"的代价
- 需要评估高频群聊的 `refreshProjection` 性能

**不要选方案 2 作为主机制** —— 它结构上无法表达"未触发的消息"，覆盖不了你的需求。
