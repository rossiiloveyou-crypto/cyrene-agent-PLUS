# 会话恢复与运行检查点瘦身方案

> 日期：2026-09-29  
> 状态：阶段 A-C 已实施；阶段 D 已清理无生产调用的恢复辅助代码，旧格式读取仍待明确的数据迁移验收后再删除
> 范围：Cyrene（当前项目）的 Harness（智能体执行循环）、会话轨迹、运行存储和界面过程记录

## 1. 目标和边界

用户手动停止后发送“继续”，或应用崩溃后重新打开原会话再发送“继续”，都应从已落盘的会话事实开启**新的一轮模型请求**。恢复的是任务语义和安全状态，不是进程、协程或模型输出到一半的位置。应用重启本身不自动执行任务。

本次改造要同时达到四个目标：

1. 下一轮拿到已提交的消息、工具结果、未完成待办和结果未知的外部操作；结果未知的非幂等操作在执行层受到拦截，而不只是一段提醒文字。
2. 停止在每次运行检查点重写整份消息、工具输出、轮次和缓存，也停止界面反复保存不断增长的过程数组。
3. 保留工具执行前后的持久化顺序和写盘失败时的熔断语义；不能以减写盘为由自动重放结果未知的工具。
4. 旧会话仍可打开和继续；Review（文件变更审查）、子任务恢复、会话压缩与文件回退各自需要的记录不受误删。

本方案**不预设**任务结束偶发卡顿的唯一原因。它处理的是已经确认的重复全量写入，并保留后续测量空间。

## 4. 目标数据归属与写入协议

### 4.1 会话轨迹是恢复的权威来源

继续复用 `assistant`、`tool_result`、`interruption` 和会话压缩条目；增加以下窄范围事件，不做通用状态框架：

| 事件 | 何时落盘 | 最小载荷 | 用途 |
| --- | --- | --- | --- |
| `tool_started` | 权限和执行守卫通过后，实际派发工具**之前** | 运行编号、所属模型消息、工具调用编号、工具名、副作用类别、参数指纹 | 有开始记录而无确定结果时判为“结果未知”；写失败就不派发工具 |
| `task_state` | 修正后的待办列表发生变化时，且在对应工具成功结果提交之前 | 所属任务轮次、完整的**当前**待办列表 | 下一轮恢复待办；相同列表不重复写 |
| `effect_resolution` | 对结果未知的操作完成核实，或用户明确授权再次执行时 | 被处理的操作编号、核实结果或一次性授权编号 | 避免恢复投影把已核实操作重新加回，也避免授权被无限复用 |
| `presentation_delta` | 过程项完成或少量字段变化时 | 消息编号、稳定过程项编号、该项增量 | 重载界面时恢复过程展示；不承载模型执行状态 |

前两项是恢复与安全事实，必须由主进程提交。`presentation_delta` 是派生展示数据，可由界面发起，但经主进程校验后进入现有会话存储。所有新条目沿用确定性编号与按会话串行追加；投影读取时只取当前有效任务分支，编辑、重新生成和回退不能带回失效轮次的待办或授权。

工具一次调用的顺序固定为：

```text
完整模型消息落盘
  -> 工具通过权限与重复副作用检查
  -> tool_started 落盘成功
  -> 执行工具
  -> 必要的 task_state / effect_resolution 落盘成功
  -> tool_result 落盘成功
  -> 对外宣布工具结果已提交
```

从未派发的工具没有 `tool_started`，缺少结果时合成为“未执行”。已经落盘 `tool_started`、却没有确定结果的工具合成为“结果未知”；即便刚写完开始记录就崩溃、实际工具尚未执行，也保守按“结果未知”处理。明确返回 `unknown` 的工具结果同样进入未决副作用集合。写结果失败后不得继续假装成功。

当前 `confirm_uncertain_effect` 的“允许再执行一次”不能简单持久化为“永久清除拦截”。新协议应把授权限定到一个参数指纹和一次调用：下一次匹配调用的 `tool_started` 引用并消耗该授权；若这次调用又在结果落盘前中断，形成新的未决操作。真正核实原操作的结果时，才写解除该操作的记录。并发工具不能消费同一授权两次。

### 4.2 运行文件只留小型元数据

保留运行编号、会话编号、开始/更新时间、`running`/终态状态，以及 Review 和启动崩溃对账确实需要的字段。运行开始、终态各写一次；索引仍按现有策略维护。

运行索引只是查找加速层，不能成为崩溃对账唯一入口。当前索引缺失或损坏时不会扫描运行文件重建；瘦身时应补上从小型运行元数据文件重建索引的路径，否则会漏掉待标记为中断的运行。

`messages`、`state`、`toolOutputs`、`rounds`、`cache`、完整请求快照和随工具状态变化重写的 `toolCalls` 不再作为新运行的持续检查点。工具完整输出继续使用已有独立输出存储；当前轮的轮数、缓存周期和故障计数留在内存。旧格式保留只读兼容，直到投影和迁移路径稳定，**不批量删除用户的旧运行文件**。

### 4.3 下一轮统一重建

手动停止和崩溃重启都走同一条下一轮入口：

1. 按现有会话轨迹投影重建模型可见消息；为中断工具补“结果未知”或“未执行”的模型可见结果。
2. 在当前有效任务分支取最近一次 `task_state`，重建未完成待办；结合 `tool_started`、`tool_result` 和 `effect_resolution` 重建未决副作用。
3. 在构造 `HarnessInput` 时把待办与未决副作用放入 `initialState`。现有恢复文字可以继续帮助模型理解情况，但执行层的指纹拦截必须读到同一份未决集合。
4. 新运行使用新的运行编号和新缓存周期。应用重启后只展示可继续的原会话，用户发“继续”或提出新要求才启动模型。

旧会话没有新事件时，投影暂时回退到旧运行文件的工具状态和旧界面快照的待办；新格式一旦存在，以新轨迹为准，不能把两套来源的同一工具或待办重复计入。

当前启动时的崩溃对账异步进行，不阻塞新消息。新方案要在**某会话第一次读取或派发新运行之前**，等待该会话幂等完成运行状态与中断边界对账；其余会话无需等全局扫描。这样“继续”不会先读到缺少中断边界的旧轨迹。

### 4.4 展示和轨迹快照

模型流式文字与思维过程的逐字变化先只留在内存；完整模型步骤结束时提交正式消息。用户主动停止时，可额外保存已收到的半截文字为**过程展示**，不冒充完整的模型回答；硬崩溃可能丢失尚未提交的半截文字。

过程消息、工具卡与推理块按稳定编号增量更新或合并写入。现有 `presentation_patch` 可继续承载兼容读取和少量最终字段，但不再每次附带全部旧数组，也不再把整份补丁编码进幂等键。终态只等待必要的最终正文/展示状态落盘，再发送现有“运行已持久化”确认；不能先确认再写。历史过程项通过投影重建。

当前第一条 `running` 展示补丁早于模型轨迹条目；如果模型尚未产出完整消息就崩溃，展示补丁没有可附着的正式消息。目标行为明确为：开局占位只作在线展示，重启后根据运行状态和中断边界显示中断信息，不把孤立展示补丁伪装成模型回答。

当前正式轨迹追加会同步文件，展示补丁追加只等待普通文件追加。新方案中间展示增量可以保持尽力保存；**终态落盘确认**所依赖的最后一条展示记录应走可靠追加路径并完成文件同步，明确区分两种保证。此处的同步只发生在必要的终态记录上，不恢复每个过程事件的全量同步写入。

`ConversationTranscriptStore.checkpoint()` 目前会写完整轨迹快照。JSONL 仍是权威记录，快照写失败可由日志重放恢复，因此不再每个运行终态同步等待它；改为会话写入队列空闲时、达到新增条目或字节阈值后整理，并避免后台整理抢在新的权威追加之前。受控退出时尽力完成已排队整理，硬退出靠日志重放。会话级压缩检查点及其“提交后才能继续请求模型”的边界仍保留。

## 5. 实施顺序

### 阶段 A：建立替代恢复协议

1. 扩展轨迹条目类型、写入校验、快照/归档/回退读取和投影；增加 `tool_started`、`task_state`、副作用处理事件。运行索引缺失/损坏时可由元数据重建，并为首次读取设置按会话的崩溃对账栅栏。
2. 工具派发前等待开始记录落盘；待办变化及用户授权在相应成功结果之前落盘。把原检查点的“保存失败即停止”语义迁到这些必要写入点。
3. 新运行构造 `initialState`；旧运行文件和旧 `runSnapshot.todos` 暂时作为兼容回退。覆盖普通停止、系统错误、强杀、重新生成与旧会话读取。

### 阶段 B：停止主运行全量检查点

1. 确认投影不再依赖新运行文件中的 `toolCalls`，中断闭合也改为读取权威工具事实；保留运行状态供启动对账与 Review 使用。
2. 将 `HarnessRunStore` 的新写入收敛为小型运行元数据，撤掉 `onCheckpoint` 对全量消息等字段的写入以及 `recordTool` 的整文件重写。
3. 审核循环内压缩、插话及工具结果失败路径：只要下一次模型请求依赖某个新事实，就必须先完成对应权威写入；无须为**不恢复同一运行**而继续保存旧缓存周期。

阶段 B 实施记录（2026-09-29）：

- 新运行改用 schema v2 的小型运行文件，只保存会话/运行编号、状态和时间戳；旧 schema v1 文件仍可读取，并保留投影回退。
- 主运行不再把 Harness 的 `onCheckpoint`、工具生命周期或循环压缩生命周期写入 `HarnessRunStore`；任务子运行自己的 `TaskSessionStore` 检查点不在本阶段改动。
- 取消或运行错误时，未闭合工具现在从当前运行的 assistant 声明、`tool_started` 和 `tool_result` 轨迹推导；v1 运行才读取旧 `toolCalls` 状态兜底。
- 循环内压缩只改变当前内存中的模型上下文；崩溃恢复继续从原始权威轨迹重建，后续会话压缩仍由 `ConversationTranscriptCompactor` 提交检查点后才进入模型请求。
- 插话在轮询器返回前先写入会话轨迹，工具结果在下一轮请求前提交；这两处没有改写入顺序。

### 阶段 C：收敛界面落盘与终态等待

1. 把累积展示补丁改为按过程项增量或合并写入，幂等键改为短而稳定的编号。
2. 待办恢复改读主进程会话状态；`runSnapshot.todos` 只承担旧会话读取，不再作为新会话执行状态的来源。
3. 最终正文和必要展示数据落盘后上报原有确认；轨迹快照改为空闲维护，不进入任务结束的等待链。

阶段 C 实施记录（2026-09-29）：

- 渲染端不再把累积数组和整份 JSON 补丁编码进幂等键；过程项按稳定 ID 写 upsert，过程文本和推理文本的纯追加部分只写新增后缀，键改为 `run:<assistantId>:<本次控制器短编号>:p<序号>`，避免接管重开时复用 assistantId 撞键。
- 投影层把增量操作折叠回普通消息数组，读取旧版全量 `presentation_patch` 的方式保持兼容；新运行不再写 `runSnapshot.todos`，待办从主进程 `task_state` 恢复，旧 v1 运行文件及旧展示快照仍由主进程读取。
- `appendPresentationNext` 只追加权威 JSONL，不再在每次过程更新后同步重建并原子写入完整投影；会话两秒没有新展示写入时再异步整理投影，任务结束不等待该快照。
- 带 terminal 状态的最终展示补丁使用文件同步追加；只有追加成功后渲染端才报告运行已持久化。检查点写入失败不会让后续写入链永久保持拒绝状态。
- 主进程与渲染端 TypeScript 检查通过；按本阶段执行约束未运行测试，写入体积和终态耗时仍需后续实测。

### 阶段 D：清理兼容代码

保留旧格式读取至少经过一次明确的数据迁移验收，再移除无生产调用的旧运行恢复辅助代码和旧格式写入分支。Review 文件基线、子任务记录、会话压缩、文件回退及独立工具输出存储逐项核对，不按“检查点”名称统一删除。

阶段 D 实施记录（2026-09-30）：

- 删除渲染端基于旧 `runSnapshot.todos` 拼接恢复提示的死代码；它没有生产调用，待办恢复已由主进程会话轨迹负责。界面正常的待办展示状态保留。
- 删除旧 `prepareHarnessRecoveryState` 运行态重建模块；新恢复路径由会话投影提供，该模块只被过时的阶段验收代码引用。阶段验收场景改为验证精简运行元数据的崩溃对账；`TranscriptSink` 和投影中的 v1 工具状态读取仍保留。
- 审计确认 `HarnessRunStore` 没有旧 schema 写入分支：新建、终态和中断对账只写 schema v2 元数据；v1 文件按只读兼容读取。未删除 v1 类型、解析、工具闭合、待办和副作用投影回退。
- Review 基线、任务子会话检查点、会话压缩边界、回退/分支轨迹、独立工具输出存储仍承担独立职责，保留。
- 尚无明确的数据迁移验收记录，因此不删旧格式读取分支及用户的旧运行文件；阶段 D 的兼容读取清理仍未完成。本轮未运行测试，写入体积和终态耗时仍待实测。

## 6. 验收场景与可观察指标

- 手动停止后发“继续”：模型看到已提交的消息、工具结果和当前待办；执行层确实拦截同参数的未决非幂等操作。
- 工具开始记录已落盘后强杀：重启原会话可区分“结果未知”和“未执行”；用户授权最多覆盖一次匹配派发，且授权后再次中断会重新变为未决。
- 待办更新、插话、会话压缩、编辑或重新生成后继续：只恢复当前有效分支的状态，不丢已确认事实，不串入失效分支。
- 长任务结束：运行 JSON 的体积不再随消息和工具输出增长；每轮写入字节主要随**新增事实**增长，终态不等待此前排队的整份展示补丁和全量轨迹快照。
- 老会话照常打开、查看 Review 并继续；新旧轨迹混合时没有重复工具结果、重复待办或错误的“已完成”提示。
- 删除或损坏运行索引后重启：能从运行元数据识别未结算运行；第一条“继续”不会抢在该会话崩溃对账之前读取上下文。

实施前后分别记录每轮主运行文件写入次数/字节数、轨迹及展示写入次数/字节数、终态到输入框恢复可用的耗时。指标用于验证改造效果，不能单凭设计断言现有偶发卡顿的根因。
